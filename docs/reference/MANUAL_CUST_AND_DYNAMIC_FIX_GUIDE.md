## 🔍 1. Анатомия ошибки: что не так с размером `cust`?

При попытке прошить кастомную прошивку на Android 15, 16 или 17 в рекавери вылетает красная надпись:
```text
assert failed: update_dynamic_partitions(state, ...)
ERROR: 1
[liblp] Block device cust size is too small (expected 872415232, got 871366656)
```

### Откуда берутся эти числа?
* **Redmi Note 5 Pro (`whyred`)**: заводской раздел `cust` = **872 415 232 байт** (ровно 832 МБ).
* **Redmi Note 6 Pro (`tulip`)**: заводской раздел `cust` = **871 366 656 байт** (ровно 830.8 МБ).
* **Разница**: ровно **1 048 576 байт (1 Мегабайт)**.

> [!NOTE]
> Разработчики прошивок собирают общий образ (**unified bouquet**) сразу для двух устройств — Whyred и Tulip. Но файл конфигурации динамических разделов они генерируют по шаблону Whyred.  
> Когда установщик запускается на Tulip, рекавери опрашивает физический чип памяти eMMC. Видя, что реальный раздел на 1 МБ меньше ожидаемого, установщик аварийно завершает работу, защищая телефон от повреждения данных.

## ⚠️ 2. Почему нельзя просто увеличить `cust` на телефоне?

Частый вопрос новичков: *«Если не хватает всего 1 МБ, почему не зайти в parted/fdisk и не сделать cust на 1 МБ больше?»*

```text
Физическая память eMMC Tulip (GPT разметка):
[ ... system | vendor | cust (830.8MB) | userdata (остальная память) ... ]
```

1. Разделы на флеш-памяти нарезаны последовательно, впритык друг к другу сектор в сектор.
2. Чтобы увеличить раздел `cust` даже на 1 МБ, нужно сдвинуть начальный сектор следующего раздела (`userdata` или `recovery`).
3. При ручном сдвиге секторов через консоль высока вероятность допустить ошибку в таблице GPT. Ошибка в 1 сектор приводит к **Hard Brick (состояние EDL 9008 / Qualcomm HS-USB QDLoader)**, поднять из которого телефон можно только замыканием тест-поинтов на плате.
4. **Вывод:** Исправить 8 байт в файле прошивки на компьютере — это **на 100% безопасно**, в отличие от ковыряния физической разметки на смартфоне.

## 📦 3. Что находится внутри архива прошивки?

Если открыть любой ZIP-архив прошивки (например, в **7-Zip**), в корне лежат два маленьких файла:
* `unsparse_super_empty.img` (размер около 4–8 КБ)
* `super_dummy.img` (размер около 4–8 КБ)

> [!IMPORTANT]
> Это **НЕ образы системы** и не Android! В них нет системных файлов.  
> Это бинарный «паспорт разметки» стандарта Google AOSP (`liblp` — Logical Partitions metadata). В нем просто записана таблица: сколько разделов создавать внутри супер-раздела, какие у них имена (`system`, `vendor`, `product`) и какие максимальные физические размеры блоков на устройстве.

## ✍️ 4. РУЧНОЙ СПОСОБ: Исправление архива своими руками

Если вы хотите сделать всё своими руками без сторонних готовых программ, вам понадобятся:
1. Архиватор **7-Zip** (или любой другой).
2. Любой бесплатный HEX-редактор: например, **HxD** ([официальный сайт mh-nexus.de](https://mh-nexus.de/en/hxd/)) или **ImHex**.

### Шаг 1. Извлечение файлов метаданных
1. Откройте файл прошивки `ваша_прошивка.zip` в **7-Zip**.
2. Извлеките на рабочий стол два файла:
   * `unsparse_super_empty.img`
   * `super_dummy.img` (если он есть в архиве).

---

### Шаг 2. Разбор байтов и замена чисел

В архитектуре ARM/x86 числа хранятся в формате **Little-Endian** (младший байт идёт первым):

| Параметр | Десятичное число | Шестнадцатеричный вид (Hex) | Байт-код в файле (Little-Endian) |
| :--- | :--- | :--- | :--- |
| **Было (Whyred)** | `872 415 232` байт | `0x34000000` | `00 00 00 34 00 00 00 00` |
| **Должно быть (Tulip)** | `871 366 656` байт | `0x33F00000` | `00 00 F0 33 00 00 00 00` |

1. Откройте `unsparse_super_empty.img` в HEX-редакторе **HxD**.
2. Нажмите **Ctrl + F** (Поиск) → выберите вкладку **Шестнадцатеричные значения (Hex-values)**.
3. Введите для поиска:  
   `00 00 00 34 00 00 00 00`
4. Замените найденную последовательность на:  
   `00 00 F0 33 00 00 00 00`
5. Повторите поиск (F3). Обычно это число встречается 1 или 2 раза (в описании блочного устройства `cust`). Замените каждое вхождение.

---

### Шаг 3. Защита целостности: пересчет контрольных сумм SHA-256

> [!WARNING]
> **Почему нельзя просто сохранить файл после шага 2?**  
> Google защитил метаданные `liblp` контрольными суммами SHA-256.  
> Если изменить байты размера и не обновить контрольную сумму, установщик рекавери выдаст ошибку:  
> `[liblp] Logical partition metadata has invalid checksum`.

Структура заголовка Google `LpMetadataHeader` устроена следующим образом:
```text
Смещение 0x00:  Магическое число 0x414C5030 ("0PLA" в hex)
Смещение 0x0C:  32 байта — SHA-256 хеш самого заголовка
Смещение 0x2C:  Размер заголовка (обычно 80 байт)
Смещение 0x30:  32 байта — SHA-256 хеш таблицы разделов
```

**Как обновляются контрольные суммы:**
1. Вычисляется хеш **SHA-256** для всей таблицы разделов (идущей сразу после 80-го байта заголовка).
2. Полученные 32 байта хеша записываются по смещению `+48` (0x30).
3. Поле хеша самого заголовка (смещение `+12`...`+44`) временно заполняется нулями (`0x00`).
4. Вычисляется хеш **SHA-256** всего заголовка (первые 80 байт).
5. Полученные 32 байта записываются по смещению `+12` (0x0C).

---

### Шаг 4. Упаковка обратно в ZIP

1. Сохраните отредактированные файлы.
2. Откройте исходный архив прошивки в **7-Zip**.
3. Перетащите обновленные `unsparse_super_empty.img` и `super_dummy.img` прямо в окно 7-Zip, согласившись на замену.
4. Готово! Архив готов к безопасной прошивке без Error 1.

## 🔍 5. Прозрачный мини-скрипт на проверку

Если вы не хотите вручную высчитывать SHA-256 хеши в калькуляторе, вот **полностью прозрачный код** на стандартном Python (без сторонних библиотек, без скачивания `.exe` из интернета).

Вы можете открыть его в Блокноте и убедиться: здесь **нет сетевых запросов, нет скрытых действий — только замена 8 байт и пересчет хеша по формуле Google**:

```python
import hashlib, struct

def fix_lpmeta_file(file_path):
    with open(file_path, "r+b") as f:
        data = bytearray(f.read())

    # 1. Заменяем размер Whyred (872415232) на размер Tulip (871366656)
    data = data.replace(b"\x00\x00\x00\x34\x00\x00\x00\x00", 
                        b"\x00\x00\xf0\x33\x00\x00\x00\x00")

    # 2. Находим заголовок Google LpMetadata (магия '0PLA' = 0x414C5030)
    magic = b"\x30\x50\x4c\x41"
    pos = data.find(magic)
    if pos != -1:
        hdr_size = struct.unpack_from("<I", data, pos + 8)[0]     # 80 байт
        tbl_size = struct.unpack_from("<I", data, pos + 44)[0]    # размер таблицы

        # Считаем SHA-256 таблицы разделов
        tbl_hash = hashlib.sha256(data[pos + hdr_size : pos + hdr_size + tbl_size]).digest()
        data[pos + 48 : pos + 80] = tbl_hash

        # Считаем SHA-256 заголовка с обнуленным полем хеша
        data[pos + 12 : pos + 44] = b"\x00" * 32
        hdr_hash = hashlib.sha256(data[pos : pos + hdr_size]).digest()
        data[pos + 12 : pos + 44] = hdr_hash

        with open(file_path, "wb") as f:
            f.write(data)
        print(f"[OK] Файл {file_path} успешно исправлен под Tulip!")

# Запуск для обоих файлов:
fix_lpmeta_file("unsparse_super_empty.img")
fix_lpmeta_file("super_dummy.img")
```

## 📱 6. Как прошить БЕЗ изменения архива (только через телефон)

Если вы вообще не хотите прикасаться к файлам прошивки и ПК, воспользуйтесь проверенным методом в рекавери:

### В OrangeFox Recovery:
1. Зайдите в **Menu** (три полоски внизу) → **Manage Partitions**.
2. Выберите раздел **Cust** → нажмите значок шестеренки/очистки → **Format / Wipe**.
3. Выберите раздел **Data** → нажмите **Change FS** → выберите **F2FS** → свайп.
4. Выберите раздел **Cache** → нажмите **Change FS** → выберите **F2FS** → свайп.
5. Перейдите во вкладку **Wipe** → **Format Data** → введите `yes`.
6. Перейдите во вкладку **Files** → выберите оригинальный архив прошивки → свайп для установки.
7. После успешной прошивки нажмите **Reboot System**.

### В TWRP:
1. **Wipe** → **Advanced Wipe** → выберите **Cust** → **Wipe**.
2. Выберите **Data** → **Repair or Change File System** → **Change File System** → **F2FS** → свайп.
3. Выберите **Cache** → **Repair or Change File System** → **Change File System** → **F2FS** → свайп.
4. **Wipe** → **Format Data** → напишите `yes`.
5. **Install** → выберите прошивку → установите.
6. **Reboot System**.
